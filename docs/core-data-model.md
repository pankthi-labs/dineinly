# Core Data Model (C5)

Everything downstream — Drizzle schema, RLS policies, tRPC routers, Realtime channels, API contracts — derives from this. Do not add entities outside this model without updating this doc first.

## Design principle

One rule, applied to every entity: **own lifecycle, own RLS policy, or queried independently → it's a table. Otherwise, it's a column.**

Optimized for a 3-developer team shipping fast: fewer joins, simpler RLS, less Drizzle boilerplate. Not textbook normalization. Still non-negotiable: tenant isolation, price/menu snapshot immutability, idempotent order submission (see `AGENTS.md` guardrails).

Every table below carries `restaurant_id` (tenant scope, RLS precondition). Soft-delete only where recovery matters: Restaurant, Staff, Menu Category, Menu Item, Restaurant Table.

## Experience Gating

`Restaurant.experience` (enum: menu/guest/counter/one, see `product.md` § Dineinly Experiences) is the field every ordering/kitchen/bill router checks to decide behavior for that tenant. Two structural consequences follow from it:

- **Menu and Counter have no Restaurant Table rows.** Neither has a Table Matrix — the Owner never creates one. Both share one QR instead: `Restaurant.qr_token`, set only when `experience` is `menu` or `counter`. Scanning it always creates a fresh, tableless Session (Session already carries no `table_id` column, so this needs no schema change to that table, only a second entry path alongside table-QR resolution). One column rather than two per-experience tokens: which behavior a scan gets (view-only Menu vs order-taking Counter) is decided by the live `experience` value read at resolve time, not by which column matched — so a restaurant switching Menu↔Counter keeps the same printed QR instead of alternating between two tokens. Provisioned idempotently by `ensure_qr_token()` (`supabase/migrations/20260730150634_add_auth_fk_and_rls_policies.sql`) whenever a restaurant becomes either; a restaurant that already has a token (its own, or from a prior stint on either) keeps it. `regenerate_qr_token()` additionally force-closes every active session when regenerating for a Menu restaurant (session is view-only, safe to end); it leaves Counter sessions running, since those can carry a real cart, placed order, or unpaid bill token a rotation shouldn't strand.
- **Counter inverts the kitchen/payment ordering.** Full-Service experiences fire to kitchen immediately and settle at the end; Counter must not let an Order Item leave `placed` until its own bill (the round it was ordered in, `Order.bill_id`) is `settled` — see Lifecycle invariants below. Kitchen/Floor/Bills/Table Matrix are all blocked outright for Menu regardless (`docs/product.md` § Dineinly Experiences), so a Menu session only ever backs guest menu-viewing, never an order.
- **Counter's Session outlives any one bill.** One/Guest cap a Session at exactly one Bill, ever — settling ends that visit's ordering for good. Counter doesn't: the guest's Session is the thing that persists for their whole physical visit (their one continuous QR-scanned identity, same as a paper token at a counter), and it can carry more than one Bill over that visit's life, one per settle-and-reorder round. See Lifecycle invariants below for exactly how a round is drawn, and `product.md` § Dineinly Experiences for the guest-facing shape this produces.

| **Bill** | restaurant_id, session_id, bill_number, daily_token (nullable), status (open/requested/settled), subtotal, tax_amount, total (all nullable until settle), settled_at, settled_by | Financial record for one settle round of a Session. Own table: a bill has its own lifecycle (open → requested → settled) distinct from the session's, and is the highest-value table to keep clean for future settlement/reprint features. **Not 1:1 with Session** — One/Guest still only ever draw one bill per session (ordering stays hard-blocked once settled), but Counter's Session can carry more than one over its life, one per settle-and-reorder round (see Experience Gating above and Lifecycle invariants). Amounts are **derived on read** for presentation (open/requested) and **frozen** only at settle — see lifecycle. Dineinly never processes payment, so no settlement-method column — only *that* it settled. `bill_number` is the human-facing identifier restaurant staff reference (unlike `id`, which stays internal) — an 8-character code (uppercase A–Z minus ambiguous I/O, plus digits 2–9: 32 chars, ~1.1 trillion values), globally unique, drawn from a Postgres sequence encoded through `encode_bill_number()` the first time this round's bill is requested. `daily_token` is the counter-only guest-facing identifier instead — a small integer, unique per restaurant per calendar day (Asia/Kolkata), backed by `restaurant_daily_tokens` and drawn atomically through `next_daily_token()`; null on every other experience. Both `bill_number` and `daily_token` are drawn together, once, the first time each round's bill row is created — for counter-experience sessions that's on order confirmation rather than waiting for a guest/staff Request Bill action, since `submit_order()` draws (or reuses) the bill itself (see Lifecycle invariants). |

## Relationships

- Restaurant 1—N everything tenant-scoped.
- Restaurant Table N—1 Session (via `session_id`). A table has zero or one active session. Merge = multiple tables share one `session_id`. **MVP:** merge only joins a **session-less (free) table** into an existing session — two already-active sessions are never merged.
- Session 1—N Cart Item, 1—N Order, 1—N Bill (One/Guest: capped at 1 in practice, see Bill above).
- Bill 1—N Order (via `Order.bill_id`) — which of the session's bills a round belongs to.
- Order 1—N Order Item.
- Menu Category 1—N Menu Item.
- Restaurant 1—N Menu Label. Menu Item.labels references Menu Label.name by value, not id — no FK, validated server-side at write time.
- Bill total = SUM(Order Items of this bill's own Orders, via `Order.bill_id`) + tax — **derived on read** for presentation (open/requested), **computed and stored** at settlement. Scoped to the bill's own orders, not every order the session has ever placed, so an earlier settled round's total is never re-summed into a later one.

**MVP pricing:** all prices are tax-**exclusive** — no inclusive mode, no `tax_mode` column. `tax_rate` is set per Menu Category (food and drinks can carry different rates, e.g. 5% vs 18%) and snapshotted onto Order Item at order time. Bill's tax breakdown (e.g. CGST/SGST) is derived by grouping the session's Order Items by `tax_rate` and splitting each slab in half for display. Rounding: every amount (line, per-slab CGST/SGST, subtotal, total) rounds independently to 2 decimal places, round-half-up — no whole-rupee round-off line. CGST/SGST within a slab round so their sum always equals the slab's rounded tax exactly (`apps/web/lib/bill-math.ts`).

## Lifecycle invariants

- **Order Item status:** `placed` → `preparing` → `ready` → `served`. `cancelled` reachable only from `placed`. Kitchen advances status only, never cancels. **Counter-experience gate:** `placed → preparing` additionally requires this item's own bill (`Order.bill_id`, not "the session's bill" — a session can carry more than one, see Bill above) to be `settled` and the item's `released_at` to be set — kitchen never starts on an unpaid counter order, nor on a paid one the guest hasn't sent yet, and an earlier round settling never waves a later, still-unpaid round's items through. Full-Service experiences (guest/one) have no such gate; kitchen fires on `placed` immediately as today.
- **Order Item release (Counter only):** once its own bill is `settled`, the guest sends each paid item to the kitchen at their own pace rather than every item firing at once — `release_order_item_to_kitchen(p_order_item_id)` sets `order_items.released_at` (null until then), scoped to the calling guest's own session via `jwt_is_guest_for_session` and to the item's own order/bill for the settled check. Idempotent: a repeat call on an already-released item is a silent no-op, same shape as `request_bill()`'s repeat-poll behavior. The Kitchen Display queue excludes a `placed` Counter item until this is set, on top of the existing settled-bill gate.
- **Order Item guest self-correction (Counter only):** the guest's own edit rights on a placed line stay open for as long as nothing has fired to kitchen — i.e. until the item's own bill settles, not until it's confirmed (Full-Service has no such window; kitchen fires on `placed` immediately there, so the guest is locked out at confirm and only Waiter/Manager/Owner can touch a line from then on, `product.md` § Order Lifecycle). `set_order_item_quantity(p_order_item_id, p_quantity)` covers it: scoped to the calling guest's own session via `jwt_is_guest_for_session`, rejects once the item's bill leaves `open`/`requested`, and decrease-only (`p_quantity` must be between 0 and the item's current `quantity` — raising it back up goes through Add to Cart + Confirm instead, which carries its own availability check this shortcut would otherwise bypass). Same quantity-replaces-outright shape as the staff Bills tab's Counter-only pill (`apps/web/server/routers/bills.ts` `setOrderItemQuantity` — nothing's reached the kitchen yet, so there's no "originally ordered" figure worth preserving): `p_quantity = 0` sets `cancelled_quantity = quantity` and `status = cancelled` (irreversible, same as any other full cancel); anything else replaces `quantity` outright and clears `cancelled_quantity`/`waived_quantity` back to 0. Gated to `status = 'placed'` at the same atomic `update ... where` as every other row here.
- **Guest-facing status** (derived, never stored): Full-Service (one) shows `Preparing` → `Partially Served` → `Served`. Guest-experience restaurants never show this at all — nothing in Dineinly ever advances an item's status for that experience, so a ladder would just hang. Counter shows `Awaiting Payment` → `Ready to Send` → `Preparing` → `Ready for Pickup` — `Awaiting Payment` for every item until its own bill is `settled` (the payment gate above), `Ready to Send` for a settled item not yet released, only then does the ladder move to `Preparing`.
- **Confirm cart:** atomically create Order + Order Items from Cart Items, then delete those Cart Items. Guarded by Order's `idempotency_key`. **Counter-experience addition:** the same transaction also resolves which bill this round attaches to and transitions it to `requested`, drawing `bill_number`/`daily_token` if it's a brand-new one — the guest sees a token immediately rather than triggering Request Bill separately. Resolution: reuse the session's latest non-settled bill if one exists (**Counter allows repeat confirms pre-settle**, same as before — the guest can keep adding items and confirming again any time before that bill settles, each confirm creating another Order row against it); once it's settled, the next confirm draws a **fresh bill** instead of being blocked — this is what lets a Counter guest order, pay, and order again on the same session/token without a new QR scan (see "Settle bill" below for the One/Guest contrast). Kitchen never starts on any of these until their own bill settles regardless (Order Item status gate above), so there's no premature-fire risk. The guest never sees repeat-confirms-within-one-round as separate orders (see `product.md` § Dineinly Experiences, guest-facing status) — one payable total, one pickup, per round. Full-Service experiences (guest/one) already allowed multiple orders per session as normal rounds of a sit-down meal, all against the session's one eventual bill; Counter's *within-a-round* repeat confirms work the same way underneath, just gated on settle instead of course pacing — Counter's difference is only that a new round can start *after* settle too.
- **Availability change:** affects future orders only. Existing Order Items are immune by construction (snapshot).
- **Request bill:** create/mark the current round's Bill `requested`, snapshot current tax rates onto it. Guests can request anytime; displayed totals are derived on read from that bill's own Order Items until settle. On a brand-new bill's first request, also draws a `bill_number` and backfills `Order.bill_id` onto every order in the session still missing one (One/Guest: every prior round, since they only ever draw one bill — see Bill above; a no-op for Counter, whose bill is already drawn and every order already attached by Confirm cart) — later requests for the same round are pure status/rate re-snapshots and never redraw or re-backfill.
- **Settle bill:** compute and store subtotal/tax/total from this bill's own orders (`Order.bill_id`, not the whole session), `status = settled`. Requires a prior Request Bill — the status ladder is always `open` → `requested` → `settled`, never a direct `open` → `settled` skip (`apps/web/server/routers/bills.ts` `settle` rejects settling a bill with no row yet). One/Guest: a settled bill never reopens for ordering — `submit_order()` (`supabase/migrations/20260730150634_add_auth_fk_and_rls_policies.sql` § 9) rejects any further order once their session's one bill is `settled`, guest or staff alike, since there is no next round for them; the frozen total must never silently drift, and the next QR scan on that table only opens a fresh session once staff has closed this one (see Close session, and `resolve_qr_token` § 8 — a closed session is never `active`, so a scan always creates a new one, never reopens the old). **Counter is the exception**: `submit_order()` never raises on a settled bill for it — ordering again just draws the next round's bill (see Confirm cart above), on the same session, no rescan or staff action needed.
- **Close session:** requires every one of the session's bills `settled` (at least one, and none still open/requested — a session that never drew a bill at all has nothing settled to close out) and no in-progress orders across any of them (every Order Item `served` or `cancelled`) → `status = closed`; free every table pointing at the session — a merged session can span more than one (`session_id` cleared immediately, by `close_session()`, § 14); hard-delete any unfired Cart Items for that session. One atomic function (`close_session(p_session_id)`), not the lazy "cleared on next scan" this doc described before that function existed — `resolve_qr_token`'s own defensive re-check (§ 8: "a session_id left over from a closed session is treated the same as no session at all") still holds as a second line of defense, but `close_session()` itself frees the table immediately so Table Matrix shows it free without waiting for a scan. **One/Guest only** — an occupied table needs a physical bussing step before the next party is seated, which no automated signal can confirm, so this stays an explicit Waiter/Manager/Owner action; see `close_idle_counter_sessions()` below for how Counter's tableless sessions close instead.
- **Force-terminate session:** staff (waiter/manager/owner) may force-close an abandoned session (walkout) — frees the tables. Every open or requested `Bill` row for the session is deleted (voided) rather than settled; any already-settled bill (an earlier Counter round) is left untouched.
- **Close idle Counter sessions:** `close_idle_counter_sessions(p_idle_minutes default 30)`, swept by `pg_cron` every 5 minutes — Counter has no physical table to reclaim and no guest-facing "I'm done" action, so a session just stops being touched once the guest has paid and collected everything (`product.md` § Dineinly Experiences). Eligible: every one of the session's bills settled (at least one), every order item `served`/`cancelled`, and the later of the last bill's `settled_at` or the last order item's `updated_at` is more than `p_idle_minutes` in the past. Staff/Dineinly Admin can still force-terminate a Counter session manually at any time (e.g. at closing, for one a guest never came back to claim) — the sweep only ever handles the ordinary case.
- Bill cardinality per session: **One/Guest — exactly one, ever.** **Counter — one or more, sequential** (never more than one open/requested at a time; see Confirm cart above). No split bills (concurrent, per-guest checks within one round) in MVP — see the Split Bill row under Deferred.
- **Staff invite:** an `invited` row can complete its first sign-in only within 24h of `invited_at` (`resolve_staff_signin`, `supabase/migrations/20260730150634_add_auth_fk_and_rls_policies.sql` § 10). Past that, sign-in fails the same generic way as an unknown email — an Owner/Manager/Admin must resend (`resend_staff_invite`, § 15, or re-save the owner-contact form) to reset `invited_at` and reopen the window before the invitee can sign in.
