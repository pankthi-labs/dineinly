# Core Data Model (C5)

Everything downstream — Drizzle schema, RLS policies, tRPC routers, Realtime channels, API contracts — derives from this. Do not add entities outside this model without updating this doc first.

## Design principle

One rule, applied to every entity: **own lifecycle, own RLS policy, or queried independently → it's a table. Otherwise, it's a column.**

Optimized for a 3-developer team shipping fast: fewer joins, simpler RLS, less Drizzle boilerplate. Not textbook normalization. Still non-negotiable: tenant isolation, price/menu snapshot immutability, idempotent order submission (see `AGENTS.md` guardrails).

Every table below carries `restaurant_id` (tenant scope, RLS precondition). Soft-delete only where recovery matters: Restaurant, Staff, Menu Category, Menu Item, Restaurant Table.

## Experience Gating

`Restaurant.experience` (enum: menu/guest/counter/one, see `product.md` § Dineinly Experiences) is the field every ordering/kitchen/bill router checks to decide behavior for that tenant. Two structural consequences follow from it:

- **Counter has no Restaurant Table rows.** Its QR lives on `Restaurant.counter_qr_token` instead — scanning it always creates a fresh, tableless Table Session (Table Session already carries no `table_id` column, so this needs no schema change to that table, only a second entry path alongside table-QR resolution).
- **Counter inverts the kitchen/payment ordering.** Full-Service experiences fire to kitchen immediately and settle at the end; Counter must not let an Order Item leave `placed` until its session's Bill is `settled` — see Lifecycle invariants below.
- **Menu gets exactly one Restaurant Table row.** Its package has no Table Matrix — the Owner never creates one — but the single QR shown on Venue Settings still hangs off a `restaurant_tables` row (label `"Menu"`), reusing the same `qr_token`/`resolve_qr_token` machinery every other experience's QR uses instead of a parallel system. Provisioned idempotently by `ensure_menu_qr_table()` (`supabase/migrations/20260730150634_add_auth_fk_and_rls_policies.sql`) whenever a restaurant becomes Menu; a restaurant that already has a table (its own, or from a prior stint on Menu) keeps it, so switching Menu → another experience → Menu again reuses the same QR instead of alternating tokens. Kitchen/Floor/Bills/Table Matrix are all blocked outright for Menu regardless (`docs/product.md` § Dineinly Experiences), so this table row only ever backs guest menu-viewing sessions, never an order.

## Tables

| Table | Key columns | Purpose |
|---|---|---|
| **Restaurant** | name, address, city, gst_number, state, pincode, service_charge_rate (nullable), experience (enum: menu/guest/counter/one), counter_qr_token (nullable, unique) | Tenant root. Settings folded in — read on nearly every request, no join. Tax is per-category, not per-restaurant (see Menu Category). address/city/gst_number/state/pincode are the bill header fields. `service_charge_rate` null = restaurant levies no service charge. `experience` gates ordering/kitchen/bill behavior restaurant-wide (see Experience Gating above). `counter_qr_token` is set only when `experience = counter` — the single QR guests scan to start a new order; unlike `Restaurant Table.qr_token`, resolving it never looks up an existing session, it always creates one. |
| **Staff** | restaurant_id, user_id (nullable FK to Supabase `auth.users`), email, name (nullable), mobile (nullable), role (enum: waiter/kitchen/manager/owner), pin_hash (nullable), status, invited_at, is_primary_owner | Identity + RBAC — tenant employees only. Guest is not a Staff role — guests never have accounts (see AGENTS.md). Dineinly Admin is not a Staff row either — it's a platform-level Supabase Auth identity carrying a privileged claim, authorized by RLS from that claim; keeping it out of Staff avoids a nullable `restaurant_id` and RLS special-casing. `pin_hash` is floor/kitchen attribution only — never a DB auth factor. `user_id` is the Supabase Auth identity that actually logs in (Email OTP for Owner/Manager, shared station account for Kitchen/Waiter) — RLS matches `auth.uid()` against it. Unique on `(restaurant_id, user_id)` where not null and not removed: one identity, at most one active Staff row per restaurant, but it can still staff several restaurants. Not a typed Drizzle FK — `auth` is a Supabase-owned schema, so the constraint is hand-written SQL (see `docs/architecture.md` § Data). `name`/`mobile` are populated only when Dineinly Admin creates a restaurant and invites its owner (Restaurants Directory); other invite paths (Owner/Manager inviting Waiters, Kitchen, other Managers) leave them null. `invited_at` starts a 24h sign-in window on every invite/re-invite — an `invited` row past that window can't complete its first sign-in until an Owner/Manager or Dineinly Admin resends the invite (`resend_staff_invite`, `supabase/migrations/20260816164344_add_staff_roster_rpcs.sql` § 15, or re-saving the Restaurants Directory's owner-contact form, which bumps it the same way); see Lifecycle invariants below. `is_primary_owner` marks the restaurant's one owner-contact owner — unique per restaurant among `role = owner` (partial unique index). Name/email/mobile are editable from the Restaurants Directory only until the primary owner's first sign-in (`status` flips `invited` → `active`); after that they're immutable there — `admin_create_restaurant`/`admin_update_restaurant`, atomic Postgres functions (`supabase/migrations/20260730150634_add_auth_fk_and_rls_policies.sql` § 6), enforce the lock. Reassigning the primary owner to someone else is a Staff Roster capability: `reassign_primary_owner` (`supabase/migrations/20260816164344_add_staff_roster_rpcs.sql` § 15c, current primary owner or Dineinly Admin only) moves `is_primary_owner` to another existing active Owner-role staff row, atomically — a pure handoff, both rows keep `role = 'owner'`; the target must already hold `role = 'owner'`, so anyone else is promoted to Owner first via `update_staff`, and downgrading the outgoing owner's role afterward is that same `update_staff` path, not part of this RPC. |
| **Restaurant Table** | restaurant_id, label, qr_token, session_id (nullable FK), status | Physical floor plan — a table guests sit at. Full-Service experiences (guest/one) have one row per physical table; Menu gets exactly one row, its universal QR (see Experience Gating above); counter-experience restaurants have zero rows here, they use `Restaurant.counter_qr_token` instead. QR is 1:1 static, folded as a column. `session_id` = the table's current active session; merge = multiple tables pointing at the same session. `status` (active/archived) is a soft-delete from the Table Matrix — hiding a table keeps its `qr_token` and row intact (recreating it would mean reprinting a new QR code). Edit, regenerate, and hide are all only allowed while `session_id` is null — an occupied table's config can't change, so a live session never goes invisible or gets its printed QR invalidated mid-visit. |
| **Table Session** | restaurant_id, status (active/closed), opened_at, closed_at | One dining visit. Groups the shared cart, all orders, and the bill for that visit. |
| **Menu Category** | restaurant_id, name, sort, tax_rate | Menu grouping and display order. Own table for stable IDs and reordering. `tax_rate` lives here, not on Restaurant — food and drinks are taxed at different rates. |
| **Menu Label** | restaurant_id, name (unique per restaurant) | The restaurant's own bounded label vocabulary (e.g. Chef Recommended, Seasonal) — Owner/Manager manages it from Menu Desk, independent of any one dish. Queried independently (populates the dish form's checkbox list), so its own table, not a column. |
| **Menu Item** | restaurant_id, category_id, name, description, price, prep_time (enum, bucketed ranges), serving_size (enum), diet (enum), availability, labels (text[] of Menu Label names), offers_spice/offers_salt/offers_ice (booleans) | Sellable catalog item. No `sort` — only Menu Category has a stable display order; dishes within a category list alphabetically. `labels` stores the chosen names directly, not label ids — no join table — but every value is validated server-side against that restaurant's Menu Label set. `offers_spice`/`offers_salt`/`offers_ice` only gate whether the guest sees that preference at order time; they never affect price and carry no value themselves — the guest's actual choice (mild/regular/extra spicy, etc.) lives on Cart Item / Order Item, not here. |
| **Cart Item** | restaurant_id, session_id, menu_item_id (live FK), quantity, spice/salt/ice, added_by_type (enum: staff/guest), added_by_staff_id (nullable) | Live shared cart, pre-confirm. | **Order** | restaurant_id, session_id, placed_at, placed_by_type (enum: staff/guest), placed_by_staff_id (nullable), idempotency_key (unique) | One confirmed round, sent to the kitchen. `placed_by_staff_id` is set to the Staff id when a waiter/manager/owner places it, null for a guest — `placed_by_type` states which explicitly. `idempotency_key` blocks duplicate orders from retries or repeated taps. |
| **Order Item** | order_id, item_name, unit_price, tax_rate, diet, quantity, spice/salt/ice, status (placed/preparing/ready/served/cancelled), waived_quantity (int, default 0, 0..quantity), cancelled_quantity (int, default 0, 0..quantity, waived_quantity + cancelled_quantity <= quantity), menu_item_id (nullable soft ref) | Kitchen fulfillment line. **Snapshots** name/price/diet/tax_rate at order time — later menu, category, or tax-rate edits never alter past orders or bills. Also serves as the bill line item. `waived_quantity` is a Bills tab correction (`product.md` § Bills tab "Waive an order item") — the bill math (guest bill, staff bill, settle, PDF) only ever counts `quantity - waived_quantity - cancelled_quantity` of this row, down to zero the same way a fully `cancelled` row is excluded, but status/quantity stay untouched so the kitchen/serve history isn't rewritten. `cancelled_quantity` is the partial-quantity form of cancel (`product.md` § Bills tab "Correct eligible order items") — only settable while status is still `placed`, also excluded from the kitchen queue; reaching `quantity` additionally sets `status = cancelled`, which is irreversible. Both are adjustable until the bill settles (cancelled_quantity only until status leaves `placed`). |
| **Bill** | restaurant_id, session_id (1:1), bill_number, status (open/requested/settled), service_charge_rate (snapshot), service_charge_waived, subtotal, tax_amount, service_charge_amount, total (all nullable until settle), settled_at, settled_by | Financial record for the session. Own table: a bill has its own lifecycle (open → requested → settled) distinct from the session's, and is the highest-value table to keep clean for future settlement/reprint features. Amounts are **derived on read** for presentation (open/requested) and **frozen** only at settle — see lifecycle. Dineinly never processes payment, so no settlement-method column — only *that* it settled. `bill_number` is the human-facing identifier restaurant staff and guests reference (unlike `id`, which stays internal) — an 8-character code (uppercase A–Z minus ambiguous I/O, plus digits 2–9: 32 chars, ~1.1 trillion values), globally unique, drawn from a Postgres sequence encoded through `encode_bill_number()` the first time a session's bill is requested; collision-free by construction, so it doesn't need retry-on-conflict logic. For counter-experience sessions, this same `bill_number` is the guest's token — shown at the counter, no separate token column needed — and it's drawn immediately on order confirmation rather than waiting for a guest/staff Request Bill action (see Lifecycle invariants). `service_charge_waived` (bool, default false) is a Bills tab correction (`product.md` § Bills tab "Waive Service Charge") — while true, `service_charge_rate` is held at 0 instead of being re-snapshotted from the restaurant's rate on every `request_bill()` call, so a guest revisiting the bill screen can't silently undo a staff waiver. |

## Relationships

- Restaurant 1—N everything tenant-scoped.
- Restaurant Table N—1 Table Session (via `session_id`). A table has zero or one active session. Merge = multiple tables share one `session_id`. **MVP:** merge only joins a **session-less (free) table** into an existing session — two already-active sessions are never merged.
- Table Session 1—N Cart Item, 1—N Order, 1—1 Bill.
- Order 1—N Order Item.
- Menu Category 1—N Menu Item.
- Restaurant 1—N Menu Label. Menu Item.labels references Menu Label.name by value, not id — no FK, validated server-side at write time.
- Bill total = SUM(Order Items in the session) + tax + service charge — **derived on read** for presentation (open/requested), **computed and stored** at settlement.

**MVP pricing:** all prices are tax-**exclusive** — no inclusive mode, no `tax_mode` column. `tax_rate` is set per Menu Category (food and drinks can carry different rates, e.g. 5% vs 18%) and snapshotted onto Order Item at order time; `service_charge_rate` stays a static per-restaurant setting. Bill's tax breakdown (e.g. CGST/SGST) is derived by grouping the session's Order Items by `tax_rate` and splitting each slab in half for display. Rounding: every amount (line, per-slab CGST/SGST, service charge, subtotal, total) rounds independently to 2 decimal places, round-half-up — no whole-rupee round-off line. CGST/SGST within a slab round so their sum always equals the slab's rounded tax exactly (`apps/web/lib/bill-math.ts`).

| Would-be table | Folded into | Why |
|---|---|---|
| Restaurant Settings | Restaurant (columns) | 1:1, read every request — no benefit joining. |
| QR Code | Restaurant Table (`qr_token` column) | 1:1, never queried on its own. Rotatable in place (regenerate overwrites `qr_token`) — not append-only, no history kept. |
| Cart | Cart Item (`session_id` FK directly) | 1:1 with session, no fields of its own. |
| Bill Line Item | Order Item (already a snapshot) | Duplicate data — Order Item already has name/qty/price frozen. |
| Guest Session | JWT claims only, no row | Guest identity is the signed token itself (`restaurant_id`, `table_session_id`); RLS checks `session.status = active`. No DB row needed. |
| Dineinly Admin identity | Supabase Auth (`auth.users.app_metadata.app_role`), no row | Not tenant-scoped, no lifecycle beyond "has the claim or doesn't" — a table would just duplicate what `auth.users` already is. ## Lifecycle invariants

- **Order Item status:** `placed` → `preparing` → `ready` → `served`. `cancelled` reachable only from `placed`. Kitchen advances status only, never cancels. **Counter-experience gate:** `placed → preparing` additionally requires the session's Bill to be `settled` — kitchen never starts on an unpaid counter order. Full-Service experiences (guest/one) have no such gate; kitchen fires on `placed` immediately as today.
- **Guest-facing status** (derived, never stored): Full-Service (one) shows `Preparing` → `Partially Served` → `Served`. Guest-experience restaurants never show this at all — nothing in Dineinly ever advances an item's status for that experience, so a ladder would just hang. Counter shows its own mapping (e.g. `Preparing` → `Ready for Pickup`) once the payment gate above has cleared.
- **Confirm cart:** atomically create Order + Order Items from Cart Items, then delete those Cart Items. Guarded by Order's `idempotency_key`. **Counter-experience addition:** the same transaction also transitions the session's Bill to `requested` (drawing its `bill_number`/token if not already drawn) — the guest sees a token immediately rather than triggering Request Bill separately.
- **Availability change:** affects future orders only. Existing Order Items are immune by construction (snapshot).
- **Request bill:** create/mark Bill `requested`, snapshot current tax/service rates onto it. Guests can request the bill anytime; displayed totals are derived on read from Order Items until settle. On the session's first request, also draws a `bill_number` (via the column's default) — later requests for the same session are pure status/rate re-snapshots and never redraw it.
- **Settle bill:** compute and store subtotal/tax/service/total, `status = settled`. Requires a prior Request Bill — the status ladder is always `open` → `requested` → `settled`, never a direct `open` → `settled` skip (`apps/web/server/routers/bills.ts` `settle` rejects settling a bill with no row yet). A settled session's bill never reopens: `submit_order()` (`supabase/migrations/20260730150634_add_auth_fk_and_rls_policies.sql` § 9) rejects any further order on a session whose bill is already `settled`, guest or staff alike — the frozen total must never silently drift. The next QR scan on that table opens a fresh session once staff has closed this one (see Close session, and `resolve_qr_token` § 8 — a closed session is never `active`, so a scan always creates a new one, never reopens the old).
- **Close session:** requires no in-progress orders (every Order Item `served` or `cancelled`) and bill settled → `status = closed`; free every table pointing at the session — a merged session can span more than one (`session_id` cleared immediately, by `close_session()`, § 14); hard-delete any unfired Cart Items for that session. One atomic function (`close_session(p_session_id)`), not the lazy "cleared on next scan" this doc described before that function existed — `resolve_qr_token`'s own defensive re-check (§ 8: "a session_id left over from a closed session is treated the same as no session at all") still holds as a second line of defense, but `close_session()` itself frees the table immediately so Table Matrix shows it free without waiting for a scan.
- **Force-terminate session:** staff (waiter/manager/owner) may force-close an abandoned session (walkout) — frees the tables. Any open or requested `Bill` row is deleted (voided) rather than settled; an already-settled bill is left untouched.
- **One bill per session** — no split bills in MVP.
- **Staff invite:** an `invited` row can complete its first sign-in only within 24h of `invited_at` (`resolve_staff_signin`, `supabase/migrations/20260730150634_add_auth_fk_and_rls_policies.sql` § 10). Past that, sign-in fails the same generic way as an unknown email — an Owner/Manager/Admin must resend (`resend_staff_invite`, § 15, or re-save the owner-contact form) to reset `invited_at` and reopen the window before the invitee can sign in.
